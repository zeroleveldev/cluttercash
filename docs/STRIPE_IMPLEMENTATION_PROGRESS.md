## Original architecture findings and continuation design (partly implemented above)

`worker/src/worker.js` authenticates existing hashed invites or hashes the anonymous `X-ClutterCash-Device` bearer. Unregistered devices map to `device:<hash>`. All quota operations use the `BetaUsageLimiter` Durable Object named `global`. `/reserve` atomically checks lifetime anonymous count (3), trial/network capacity and global daily provider budget, and reserves the attempt before provider work in one storage transaction. Existing manually approved access is not a paid subscription and must not silently become one.

Smallest secure continuation:
1. Choose independently authenticated paid-user identity only for subscribers (e.g. verified-email login). Create durable server-owned binding from that principal to Stripe customer/subscription; do not trust client-supplied customer, Price or account IDs. Anonymous device token may link the current browser AFTER paid-owner authentication, but is NEVER sole recovery proof. Existing emailed owner approval activates a browser, not subscriber ownership.
2. Hosted Checkout created server-side with `mode=subscription`, one owner-verified test monthly USD 199-cent Price, quantity 1, fixed allowed success/cancel URLs and server-owned principal association. Verify retrieved Price currency, unit amount, recurring month/interval count, active state and test mode. No client-selected amount or Price. Checkout success redirect only displays pending/server-read status; grants nothing.
3. Mount raw-body signature route independently of browser invite/CORS authorization; reject oversized streams early. Persist valid work durably before acknowledging; on persistence failure return retriable non-2xx. Do not acknowledge payments as processed while this foundation lacks a ledger.
4. On `invoice.paid`, retrieve authoritative subscription/invoice with pinned API version and test key; require correct customer binding, configured recurring Price and eligible active subscription before normalization. Handle current API invoice/subscription item shapes explicitly; do not guess old `invoice.subscription` layouts. Reject prorations, unrelated/manual invoices and unrecognized billing reasons until policies are defined.
5. In the SAME global DO transaction, deduplicate event ID AND invoice/object grant identity; record an eligible period grant of 10 with Stripe-derived start/end, then mark processed. Also protect against distinct invoices granting the same subscription period twice. Event `created` is not ordering proof. Reconcile current Stripe state; late historical deliveries must not reset current consumption.
6. Add paid principal reservation to the existing `/reserve` transaction, so credit decrement and provider-budget reservation succeed/fail together. Do not debit in a separate DO then reserve budget (partial consumption risk). Test simultaneous last-credit requests, repeated events/invoices, out-of-order renewals, expiry and transaction rollback in real local Durable Object runtime. Keep provider attempts non-refundable on ambiguous timeout as existing guard requires.
7. No new period credits for failed/unpaid invoices. Decide immediate cancellation versus end-of-paid-period access, refunds/disputes, duplicate subscriptions, free-versus-paid scan ordering, and rollover before coding those policies. Period-scoped storage is proposed, not approval of no-rollover behavior. Saved projects/corrections/research never depend on billing status.
